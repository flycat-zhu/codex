# OpenClaw 角色交互规则

## 概述

本文档定义了 OpenClaw 多角色工作流系统中各角色之间的交互规则，确保角色间能够有效协作，避免冲突和混乱。

## 角色交互矩阵

### 开发端角色交互

```
需求管理者 → 需求设计者 → 开发者
     ↓           ↓          ↓
   需求文档    设计文档    代码实现
```

### 测试端角色交互

```
测试管理者 → 测试设计者 → 测试执行者
     ↓           ↓            ↓
  测试策略    测试用例     测试结果
```

### 跨端交互

```
开发者 ←→ 测试执行者
  ↓          ↓
代码实现   测试反馈
```

## 交接协议

### 1. 需求管理者 → 需求设计者

**交接条件：**
- [ ] 需求分析文档已完成
- [ ] 所有需求都有唯一标识符
- [ ] 需求优先级已确定
- [ ] 需求冲突已解决或标记
- [ ] PR 已创建并合并到 main 分支

**交接内容：**
- 需求分析文档 (`docs/requirements/requirements-analysis.md`)
- 需求优先级列表 (`docs/requirements/requirements-priority.md`)
- 需求追踪矩阵 (`docs/requirements/requirements-traceability-matrix.md`)
- 需求冲突报告（如果有）(`docs/requirements/requirements-conflicts.md`)

**交接检查清单：**
1. 验证需求文档完整性
2. 确认需求标识符格式正确
3. 确认优先级合理
4. 确认 Git 分支已合并

**交接通知：**
需求设计者收到通知后，应从 `feature/requirements-analysis` 分支创建新的设计分支。

### 2. 需求设计者 → 开发者

**交接条件：**
- [ ] 系统设计文档已完成
- [ ] 架构设计已完成
- [ ] 接口定义清晰完整
- [ ] 技术选型已确定
- [ ] PR 已创建并合并到设计分支

**交接内容：**
- 系统设计文档 (`docs/design/system-design.md`)
- 架构设计文档 (`docs/design/architecture.md`)
- 接口设计文档 (`docs/design/interfaces.md`)
- 技术选型文档 (`docs/design/tech-stack.md`)

**交接检查清单：**
1. 验证设计覆盖所有需求
2. 确认架构清晰可实施
3. 确认接口定义完整
4. 确认技术选型合理
5. 确认 Git 分支已合并

**交接通知：**
开发者收到通知后，应从 `feature/design-v1` 分支创建实现分支。

### 3. 开发者 → 测试执行者

**交接条件：**
- [ ] 代码实现已完成
- [ ] 单元测试已编写
- [ ] 代码覆盖率达标（> 80%）
- [ ] 代码审查已通过
- [ ] PR 已合并到设计分支

**交接内容：**
- 源代码文件
- 单元测试代码
- 实现报告 (`docs/implementation/implementation-report.md`)
- 代码覆盖率报告

**交接检查清单：**
1. 验证代码能正常编译/运行
2. 确认单元测试全部通过
3. 确认代码覆盖率达标
4. 确认代码符合规范
5. 确认 Git 分支已合并

**交接通知：**
测试执行者收到通知后，应开始执行测试用例。

### 4. 测试管理者 → 测试设计者

**交接条件：**
- [ ] 测试策略文档已完成
- [ ] 测试计划已制定
- [ ] 测试资源已分配
- [ ] PR 已创建并合并到 main 分支

**交接内容：**
- 测试策略文档 (`docs/testing/test-strategy.md`)
- 测试计划文档 (`docs/testing/test-plan.md`)
- 测试资源分配 (`docs/testing/test-resources.md`)

**交接检查清单：**
1. 验证测试策略覆盖所有需求
2. 确认测试计划详细可执行
3. 确认资源分配合理
4. 确认 Git 分支已合并

**交接通知：**
测试设计者收到通知后，应从 `feature/test-management` 分支创建测试设计分支。

### 5. 测试设计者 → 测试执行者

**交接条件：**
- [ ] 测试用例已设计
- [ ] 测试场景已设计
- [ ] 测试脚本已编写
- [ ] 测试数据已准备
- [ ] PR 已创建并合并到测试管理分支

**交接内容：**
- 测试用例文档 (`docs/testing/test-cases.md`)
- 测试场景文档 (`docs/testing/test-scenarios.md`)
- 测试脚本 (`tests/integration/`)
- 测试数据 (`tests/fixtures/`)

**交接检查清单：**
1. 验证测试用例覆盖所有功能点
2. 确认测试场景完整
3. 确认测试脚本可执行
4. 确认测试数据充分
5. 确认 Git 分支已合并

**交接通知：**
测试执行者收到通知后，应开始执行测试。

## 反馈循环

### 设计反馈循环

**触发条件：**
- 开发者在实现过程中发现设计问题
- 设计无法实现或实现困难
- 设计存在逻辑错误

**反馈流程：**
1. 开发者识别问题并记录
2. 创建反馈文档 (`docs/feedback/design-feedback-<id>.md`)
3. 通知需求设计者
4. 需求设计者分析问题
5. 更新设计文档
6. 通知开发者重新实现

**反馈文档格式：**
```markdown
# 设计反馈 #<id>

## 问题描述
[详细描述发现的问题]

## 影响范围
[说明影响的功能模块]

## 建议方案
[提出解决方案建议]

## 优先级
[高/中/低]
```

### 测试反馈循环

**触发条件：**
- 测试执行者发现缺陷
- 测试用例执行失败
- 功能不符合需求

**反馈流程：**
1. 测试执行者记录缺陷
2. 创建缺陷报告 (`docs/testing/bug-reports.md`)
3. 通知开发者
4. 开发者分析并修复
5. 重新提交代码
6. 测试执行者验证修复

**缺陷报告格式：**
```markdown
# 缺陷 #BUG-<id>

## 缺陷描述
[详细描述缺陷现象]

## 重现步骤
1. [步骤1]
2. [步骤2]
3. [步骤3]

## 预期行为
[描述预期行为]

## 实际行为
[描述实际行为]

## 严重性
[严重/一般/轻微]

## 优先级
[高/中/低]

## 关联需求
[REQ-xxx]
```

### 需求变更循环

**触发条件：**
- 任何角色发现需求问题
- 需求不清晰或存在歧义
- 需求需要补充或修改

**反馈流程：**
1. 发现问题的角色记录
2. 创建需求变更请求 (`docs/requirements/change-requests/<id>.md`)
3. 通知需求管理者
4. 需求管理者评估变更
5. 更新需求文档
6. 通知所有相关角色

**变更请求格式：**
```markdown
# 需求变更请求 #REQ-CHANGE-<id>

## 变更类型
[新增/修改/删除]

## 原需求
[REQ-xxx] [原需求描述]

## 变更内容
[详细描述变更内容]

## 变更原因
[说明变更的原因]

## 影响分析
[分析对设计、实现、测试的影响]

## 优先级
[高/中/低]
```

## 冲突解决机制

### 冲突类型

1. **需求冲突**：需求之间相互矛盾
2. **设计冲突**：设计与需求不一致
3. **实现冲突**：实现与设计不一致
4. **测试冲突**：测试结果与预期不符

### 冲突解决流程

1. **识别冲突**
   - 明确冲突的类型
   - 确定冲突的影响范围
   - 记录冲突详情

2. **升级处理**
   - 将冲突升级到工作流协调器
   - 创建冲突报告 (`docs/conflicts/conflict-<id>.md`)

3. **协商解决**
   - 相关角色参与协商
   - 分析各种解决方案
   - 选择最佳方案

4. **更新文档**
   - 更新相关文档
   - 记录解决方案
   - 更新版本号

5. **通知影响**
   - 通知所有受影响的角色
   - 更新工作流状态

### 冲突报告格式

```markdown
# 冲突报告 #CONFLICT-<id>

## 冲突类型
[需求冲突/设计冲突/实现冲突/测试冲突]

## 冲突描述
[详细描述冲突内容]

## 涉及角色
[列出涉及的角色]

## 影响范围
[说明影响的功能和模块]

## 解决方案
[提出解决方案]

## 解决状态
[待解决/已解决/已关闭]
```

## 角色权限和限制

### 需求管理者

**权限：**
- 创建和修改需求文档
- 确定需求优先级
- 解决需求冲突

**限制：**
- 不能直接修改设计文档
- 不能直接修改代码
- 不能直接修改测试用例

### 需求设计者

**权限：**
- 创建和修改设计文档
- 选择技术栈
- 设计系统架构

**限制：**
- 不能直接修改需求文档（需要通过需求管理者）
- 不能直接修改代码
- 不能直接修改测试用例

### 开发者

**权限：**
- 创建和修改代码
- 编写单元测试
- 修复代码缺陷

**限制：**
- 不能直接修改需求文档
- 不能直接修改设计文档（发现问题需反馈）
- 不能直接修改测试用例（发现问题需反馈）

### 测试管理者

**权限：**
- 制定测试策略
- 管理测试计划
- 分配测试资源

**限制：**
- 不能直接修改需求文档
- 不能直接修改设计文档
- 不能直接修改代码

### 测试设计者

**权限：**
- 设计测试用例
- 编写测试脚本
- 准备测试数据

**限制：**
- 不能直接修改需求文档
- 不能直接修改设计文档
- 不能直接修改代码

### 测试执行者

**权限：**
- 执行测试用例
- 报告测试结果
- 记录缺陷

**限制：**
- 不能直接修改需求文档
- 不能直接修改设计文档
- 不能直接修改代码（发现问题需反馈）

## 沟通协议

### 通知机制

每个角色在完成工作后，必须：

1. **更新状态**
   - 更新工作流状态文件
   - 标记阶段为完成

2. **发送通知**
   - 通知下一个角色
   - 包含交接检查清单

3. **创建检查点**
   - 保存当前状态
   - 记录版本信息

### 文档更新规则

1. **版本控制**
   - 每次更新必须增加版本号
   - 记录更新原因和内容

2. **变更通知**
   - 更新文档后通知相关角色
   - 说明变更内容

3. **向后兼容**
   - 尽量保持向后兼容
   - 重大变更需要协商

## 质量保证

### 交接质量检查

每次角色交接前，必须完成：

1. **文档完整性检查**
   - 所有必需文档已生成
   - 文档格式正确
   - 文档内容完整

2. **内容质量检查**
   - 内容符合规范
   - 逻辑清晰
   - 无重大错误

3. **Git 状态检查**
   - 代码已提交
   - PR 已创建
   - 分支状态正确

### 反馈质量要求

1. **反馈必须具体**
   - 明确指出问题
   - 提供具体示例
   - 说明影响范围

2. **反馈必须可操作**
   - 提供解决方案建议
   - 说明优先级
   - 给出时间估算

3. **反馈必须及时**
   - 发现问题立即反馈
   - 不要积累问题
   - 定期同步状态

## 最佳实践

### 1. 及时沟通

- 发现问题立即反馈
- 定期同步工作进度
- 重大决策及时通知

### 2. 文档先行

- 先写文档再实现
- 文档与代码同步更新
- 保持文档版本一致

### 3. 验证充分

- 每个阶段完成后充分验证
- 交接前完成检查清单
- 不要跳过验证步骤

### 4. 版本控制

- 所有文档纳入版本控制
- 使用有意义的提交消息
- 保持分支清晰

### 5. 持续改进

- 记录问题和解决方案
- 优化工作流程
- 更新交互规则
